01 · Integrity

One ordering rule, enforced everywhere.

A chunk is only marked complete in the database after its bytes have been fsync'd to disk. The database runs in WAL mode with synchronous=FULL — so a committed complete row is a durable promise that the bytes really are on the platter.

01 — WRITE

Bytes land

Data is written into the staged .mothpart file — never the final name.

02 — FSYNC

The OS flushes

The OS is told to push the bytes all the way down to the disk. Not "soon". Now.

03 — COMMIT

Only then, complete

The chunk is marked complete in the database — a row that survives a power cut.

Re-digested on restart

Recovery re-hashes every completed chunk on startup. Anything that doesn't match is discarded and re-downloaded — silent disk rot gets caught, not trusted. capped at 512 MB per download; larger downloads are sampled

Source identity

ETag and Last-Modified go back as If-Range. If the remote file changed, progress is discarded — bytes from two versions of one file must never be stitched together.

Checksums, four of them

MD5, SHA-1, SHA-256 and SHA-512 verification — plus a fast CRC-32 watching for chunk-level corruption in flight.

Honest about weak validators

An ETag is a server validator, not a cryptographic checksum. A digest without an expected value is a fingerprint, not proof. The interface draws that line instead of hiding it.

02 · Engines

Three engines. One queue.

HTTP, media and torrents share the same queue, the same status vocabulary, the same controls. Each carries its own badge, because each counts progress its own way.

The range engine

  • Parallel Range requests — up to 32 connections per download, chunk planning sized to the file.
  • GCRA rate limiting — the exact long-run rate with no bursts, enforceable even at very low speeds where a naive token bucket stalls.
  • Refreshed links keep progress — replace a dead URL; partial data is kept when size and a strong ETag still match.
  • A server that refuses Range is labelled no resume up front, and downloads as a single stream.

The media pipeline

  • Stream selection — video quality, audio output format, subtitle languages, filename templates.
  • Playlist browsing with per-entry thumbnails and titles.
  • Output is staged, then the decode is verified before the video is declared finished.
  • No HLS / .m3u8 support. Segmented playback needs a playlist parser, a segment fetcher, AES-128 decryption and a container remux — a project in its own right.
  • Content-agnostic transport. Streams are passed through as bytes; Moth does not inspect, filter, or refuse a payload by what it contains — and never decrypts one.

Torrents through Transmission

  • v1 / v2 magnets and .torrent files, through a bundled Transmission daemon.

  • Torrents carry their own badge — Transmission tracks pieces, not chunks.
  • Windows x64 only — the only platform whose package bundles the daemon.

06 · Connect

It meets your browser where it is.

A desktop app cannot silently intercept Chrome's downloads — there is no OS hook for it. So Moth ships an extension, the same way IDM, JDownloader and Free Download Manager do. It pairs with the running app over a loopback-only endpoint, guarded by a 32-byte CSPRNG token compared in constant time. Moth only listens while it is running.

ChromeEdgeBraveOperaVivaldi · MV3 SWFirefox 115+

Guided Chrome setup. Moth creates a folder on your desktop with the unpacked extension and a visual guide — load it once, and every link is one click from the queue.

07 · Security

Bounded by design.

The whole attack surface, stated small enough to check.

Loopback only

The ingest endpoint binds 127.0.0.1 — never 0.0.0.0. A download manager that takes commands from the LAN is a remote code execution vector.

Constant-time token

32 bytes from a CSPRNG, compared in constant time. Pairing is a shared secret, not a handshake you can guess.

Validated payloads

Every renderer → engine payload passes a zod schema before anything acts on it.

Contained paths

Every path derived from remote data stays inside the download root. A hostile Content-Disposition cannot escape.

No server in the middle

File bytes and file metadata never travel through any network service. There is no cloud.

No content policy

Moth moves bytes, not judgements. It never inspects, filters or refuses a payload by what it contains — and it never decrypts one.

09 · Limitations

Stated plainly.

What Moth won't do — because a product that hides these is worse than one that does.

BitTorrent is Windows x64 only. No tracker administration, RSS/search, configurable seeding or quotas.
HLS / DASH rides on yt-dlp — encrypted-segment support is whatever yt-dlp provides.
Protected media is transferred, never decrypted. No key handling, no unwrapping, no licence logic — Moth is a transport, not a decoder.
No cookie or session import. Sites behind a login need the extension, which forwards Cookie and Referer for that request.
A server that refuses Range can't be resumed — single stream, restart from zero. Labelled up front.
No resume when the remote file changed — progress is discarded rather than risking mixed content.
The ingest endpoint is IPv4 loopback only, and can only write inside a configured folder.
Self-update is Windows-only and unsigned — SmartScreen will complain on first run. macOS and Linux update from the releases page.
Recovery re-verification is capped at 512 MB per download; larger downloads are verified by sampling on startup. An advanced setting can change the cap.
Multi-threaded transfers cap at 32 connections per download.
Tags are written for ID3v2.3 and MP4 only — reading is broader.
One default folder plus named library roots — no mirroring, no remote backup.

A product that hides these would be worse than one that does.
